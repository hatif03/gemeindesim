GemeindeSim: a bilingual civic what-if simulator on Apertus 1.5

Hack Apertus 2026 · Track 2B · Team 1ne · 5–15 Oct 2026 · github.com/hatif03/gemeindesim · videos youtu.be/ZdXAJjCUhZI and youtu.be/BZnqYIDV63Q · judged on the CSCS API · numbers from logged experiments, sources in section 7

1. Why this exists, and what we found

Problem. Swiss voters decide on written text, and the text can be wrong or misread. In 2019 the Federal Supreme Court annulled the 2016 Heiratsstrafe vote because the booklet said about 80,000 couples were affected when 454,000 were [50]; a 2023 parliamentary audit found the booklet's four-eyes check is not always done by people with the right expertise [51]; 43 % of 1,513 respondents could not say what the November 2018 vote was about [52]. In many of the 2,110 municipalities the assembly sees 4–8 % of eligible voters, so the written proposal is what most people read [58]. We found no actor that pre-tests the wording of an official text with simulated readers before it is published.

Similar applications, and what they are used for. Simulated people and AI-assisted listening are used in research and, increasingly, in government and market research; the reference numbers point to section 7.

What we built. GemeindeSim reads a vote text in German and French, spawns a fictional town of up to 25 residents who talk, move, change mood and form a stance on a pixel-art map, and writes a closing report on who is affected and why – never how to vote. It is a what-if and pre-test tool, not a vote predictor. We also used the town as a test bench for Apertus 1.5 (8B and 70B, two endpoints): more than 20,000 logged calls and trials, 32 experiment scripts, 48 instrumented simulations.

What we found. Apertus is an excellent speaker (112/112 resident lines in the right language; it abstains when a premise is missing; no voting advice in 30 tests) and an unreliable decider: asked for a stance, all 15 residents said yes, even with no persona; on 54 real Swiss federal votes the simulated electorate was 34–37 points too favourable and the 8B followed an official recommendation 98 % of the time; both sizes defined Steuerfuss wrongly and failed a one-step percentage. The design follows: the model voices; the application owns the stance, the arithmetic and the sources. Effect (same seeds): valid citations 0/159 → 100 %, reports asserting an outcome 12/30 → 0/30, residents whose words match their stance ≈0.5 → ≈0.9, a town that starts with real disagreement. On a real 48-page Federal Council booklet the pipeline answered 12/14 questions correctly and abstained on every unanswerable one.

2. Architecture

Fig. 1. End to end. Blue: Apertus voices. Green: code owns. Red: code checks the model. Beige: user and screen.

Stack. Two Docker services. A FastAPI + LangGraph backend holds the standard and a two-phase (initiator/reactor) round graph; sentence-level chunking with BM25 retrieval (per-chunk language, the ballot question pinned) and an optional dense hybrid; an async model client with an adaptive concurrency limiter, retries and sentence-level streaming; a grounded 1:1 chat; token accounting; the report writer with its guardrails; a Socket.IO stream; and a multi-seed spread run. A Next.js + Phaser frontend shows the map, the event feed with citation chips, the stance poll, the influence graph, the report, a run-metrics panel and a recorder/loader for saved runs. The corpus is read-only; the only outbound call is the OpenAI-compatible LLM_BASE_URL. No personal data is used: residents are generated at run time (code draws name, role, income band, leaning and language; the model writes the persona text).

Use of Apertus

Policy parsing, personas, pro/con arguments, resident turns, impact judgement and the report: the 70B (the 8B also works) in json_object mode, thinking off, one language per completion, with an instruction-placeholder example in the resident's language (49/49 first-attempt valid, 0 % parroting; a filled example is parroted, 8B 53 %; strict json_schema breaks the 8B). DE↔FR translation of lines is a separate call; the 1:1 chat is streamed per sentence. Retrieval, numbers, stance and dynamics are plain code: no tool calls (parallel calls fail 11/11; thinking plus JSON silently skips the reasoning).

Deployability. Primary (c) Swiss-hosted endpoint: the CSCS inference API (used for judging) or the hackathon gateway; one build, three variables (LLM_NAME, LLM_BASE_URL, LLM_API_KEY); model ids are mapped between the two endpoints' styles and concurrency adapts (LLM_CONCURRENCY=auto). (a) On-premise / (b) air-gapped: point LLM_BASE_URL at any OpenAI-compatible server hosting open weights, e.g. vllm serve swiss-ai/Apertus-v1.5-8B --port 8001 on a GPU host and LLM_BASE_URL=http://host.docker.internal:8001/v1, LLM_NAME=swiss-ai/Apertus-v1.5-8B; the 8B was about 4× faster per simulation than the 70B. Honest status: all behaviours were measured on two hosted endpoints; no GPU was available, so no local run was measured (a probe script in the repository runs the same capability table against any endpoint).

Fig. 2. Stance is computed in code (weights are assumptions, not calibrated).
Code-owned controls (each added after a measured failure, section 4):
  • Stance: ideology × leaning + 0.5 × judged impact − 0.6 × computed household cost + noise (sd 0.15); thresholds ±0.15.
  • Opinion dynamics: bounded confidence (Deffuant): keep / compromise / adopt by influence; only residents who conversed move.
  • Sources: passages carry labels [P#]; a citation that does not exist is dropped; the ballot question is always in the prompt.
  • Numbers: numeral gate strips figures not in the pack or the calculator; household CHF comes from a calculator on the booklet's worked example.
  • Speech binding: last paragraph of the prompt states the code stance (“your position: for/against”).
  • Report guardrails: no asserted outcome, no vote advice, Swiss spelling (no ß), local disclaimer.

Real booklet and spread across seeds. On the 48-page Federal Council booklet of 28 Sept 2025 (83 k characters, 209 chunks, two measures) the retriever puts the gold evidence into four passages for 11/14 questions (old retriever 10/14); the 70B answered 12/14 correctly (hand-graded), abstained on 3/3 unanswerable questions and abstained wrongly only where the evidence was not retrieved: retrieval, not the model, is the bottleneck. Personas and the stance prior are drawn per seed and T=0 is not reproducible, so one run is not a result: across five 70B seeds the final share for ranges 0.00–0.80 (8B 0.00–0.40), and the poll did not change in 4 of 5 runs within three rounds. Compare-conditions (E19, 8B, three paired seeds): adding the referendum committee's counter-arguments lowers the mean stance in all three seeds (−0.28); a yes/no council recommendation does not move it consistently, because the stance never reads it.

5. Second endpoint, engineering checks and the demo run

CSCS (E20–E28). Capability matrix, throughput, long context, determinism, structured output, stance on four models, retrieve-first vs whole-booklet, the final code on 5 seeds × 2 sizes, and the grounded chat live. All v2 fixes replicate (valid citations 1.00, no asserted outcome, speech matches the code stance 0.85–0.88), and so do the Swiss-knowledge and real-vote results. Unchanged: the yes-bias (E24), one tool call, non-reproducible T=0. With the complete booklet in the chat prompt (6,000–100,000 characters) the real revenue question is answered 5/5 instead of 0/5. One build, both endpoints (E31; same code and seeds, the 5-resident 3-round run took 61 s on CSCS and 126 s on the gateway; the gateway answers 429 above 4–5 requests in flight, CSCS took 2,496 requests up to 96 in flight without one; Python used 2.2–5.0 % of the wall time, E29): ids are mapped and the limiter adapts (three iterations): 25 residents × 2 rounds took 89–97 s on CSCS and 654 s on the busy gateway.

Mentor questions, answered with measurements (E29–E32)

  • Python, async, context. The wall time is the longest chain of dependent calls (persona, impact, reflection, turn, translation) at ≈60 tokens/s; every call is async; resident prompts use at most 1.1 % of the 262 k window, so no compaction is needed; 17–25 % of prompt tokens were cached on CSCS (moving the instruction block to the front would save ≈0.3 s of a 5.5 s call but moves the speech-binding paragraph: not done).
  • Streaming, tokens, subagents. The chat streams sentence by sentence after the number gate and citation check (first text 1.5 s, whole answer 2.4 s, 0 invented figures); JSON turns and the report are not streamed (they must be complete to be validated). Tokens are counted from the endpoint's usage and shown in a run-metrics panel (in/out/cached, latency p50/p95, context use, retries, in-flight limit). Each resident is an isolated context run in parallel; there is no tool loop.

RAG against the usual baselines (E30; 14 gold questions, 209 chunks of the real booklet). recall@4 / MRR@10: our BM25 0.79 / 0.29; dense multilingual-e5-large 1.00 / 0.89; hybrid BM25 + e5-large (reciprocal rank fusion) 1.00 / 0.91; a small paraphrase model 0.71 / 0.56 (worse than BM25). n = 14 on one German document: one-question differences are noise. The hybrid is an option, off by default because it needs a 2.2 GB local model that an air-gapped deployment would have to ship.

6. Progress, limitations, reproducibility

Progress

5 Oct: audit of the inherited code (citations 0/159, outcomes asserted), instrumented baseline (E3), probes E1–E12, the yes-bias (E11) and the failed fixes (E11b, E11c), then the v2 design (code-owned stance, validated citations, numeral gate, speech binding E14–E16), the real booklet (E17), compare-conditions (E19), a repaired clean-clone build (E18) and a corrected measurement error (C1). 6 Oct: second endpoint, CSCS (E20–E28); chat wired and grounded. 7 Oct: the mentor's engineering questions (E29–E32); defaults switched to CSCS, which the judges use. 8 Oct: literature and deployment survey, the demo run recorded from the running app. 13 Oct: a fresh clone of the public repository built with Docker; recording the demo found a deployment bug (two server workers, so a run and its Socket.IO session could land on different workers and about every other run failed with “Simulation not found”): fixed with one worker and verified; ready-to-paste scenarios added; this report, the footage and the voice-over.

Limitations (what we do not claim)

  • Not a vote predictor (54 real votes; weak signal after bias correction). Stance weights are modelling assumptions, not calibrated; the stance prior produces disagreement and is not evidence that real residents would split that way. Evaluation uses one synthetic town text and one real booklet.
  • Small n: 3–5 simulations per group, 15 residents in population tests, 14 retrieval questions, 15 held-out votes; ranges, no significance tests.
  • Two hosted endpoints, a few days; latency drifts several-fold. Local and air-gapped deployment were not measured (no GPU). German/French register: a native-speaker review pack is prepared; we do not claim native review until its corrections are applied.
  • Open: the price_pressure indicator is always 0; the 8B never emits move; the backend caps residents at 25; the Linden sample is synthetic and short; real-booklet French edition untested.

Reproducibility (what a judge runs)

Clone the public repository, set three environment variables (LLM_BASE_URL, LLM_NAME, LLM_API_KEY; the defaults are the CSCS endpoint and swiss-ai/Apertus-v1.5-70B) and run make run (without make: docker compose up --build in the project directory). The app opens at http://localhost:3000 (a second port is UI_ALT_PORT; change it if 8080 is taken). LOAD replays the recorded demo run included in the repository without calling the model; PLAY opens the editor, where a text is pasted and a run started. The repository README lists ready-to-paste scenarios (German, French and English: a fire-station vote with a tax change, a swimming-pool credit, parking fees, a budget, a bike-lane trial, and a deliberately ambiguous text) with what to look for in each. Offline tests: 146, run with uv run pytest in the backend. Every experiment is a script with raw call logs, and a lab notebook records every decision including the failed attempts.

Next steps. Run the probe and a simulation on a local vLLM (8B); apply the native-speaker corrections; statistics-based personas; calibrate the stance prior on municipal results; a panel-question output so a human citizen panel (cf. Sion 2019) can check what the simulation flags.
